## 宿題

- 取り組んだレベル：基礎
- やったこと：
  `app/tools.py` の `search_glossary` の docstring の1か所だけを変更した。
  「query には調べたい用語を1つだけ入れる（例: "LoRA"）」を
  「query には調べたい用語をまとめて入れる（例: "LoRA QLoRA"）」に書き換えた。
  質問「LoRA とQLoRAの違いは？」を、変更前と変更後で3回ずつ `--trace` 付きで実行し、
  ツール呼び出し・`requests`・トークン数・回答を比べた。
- 結果：

  | | 変更前（3回とも同じ） | 変更後（3回とも同じ） |
  |---|---|---|
  | 検索の引数 | `LoRA` と `QLoRA`（2回） | `LoRA QLoRA`（1回） |
  | tool_calls | 2 | 1 |
  | requests | 2 | 2 |
  | input_tokens | 1196 | 891 |
  | output_tokens | 171 / 189 / 206 | 204 / 207 / 198 |
  | cost（平均） | 約0.00083 | 約0.00077 |

  回答は、どちらも LoRA と QLoRA の違い（量子化の有無）を正しく説明し、末尾に第2回を示した。
- 気づき・疑問：
  - docstring の1語（「1つだけ」→「まとめて」）で、モデルの引数の作り方が変わり、ツール呼び出しが2回から1回になった
  - ツールが2回でも `requests` は2だった。1回目の応答で2つの呼び出しをまとめて出していた（バッチコール）。1回に減っても、結果を読む往復が必要なので `requests` は1にならない
  - `input_tokens` が減ったのは、まとめて検索すると返る用語の数が減る（5件→2件）ためだと考えられる
  - まとめて検索しても QLoRA が返ったのは、`search_glossary` が部分一致で探す作りだから。完全一致だけの検索なら、同じ変更で QLoRA が見つからなくなる。docstring の変更は、ツール側の実装との相性に依存する
  - `cost` や `output_tokens` の差は、各3回では揺れの範囲で、効果とは言い切れない。回数を増やして確かめたい
  - 疑問：（自分の言葉で書く。例：INSTRUCTIONS の「必ず検索する」の行を消すと、検索せずに答えるか）
